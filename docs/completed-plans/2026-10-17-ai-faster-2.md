## Scope and Decisions

The objective is less serial work during computer-player turns and the surrounding simulation.
The user permits behavioral changes, including less frequent strategic reconsideration.
Deterministic execution, command legality, and save/load consistency remain mandatory.

This plan covers all eight proposed areas:

1. Reuse calculations within a turn.
2. Share compatible pathfinding work.
3. Reduce candidate searches.
4. Reconsider strategic decisions less often.
5. Maintain spatial indexes.
6. Continue valid ongoing orders.
7. Reduce temporary allocations and repeated sorting.
8. Optimize non-AI turn systems that contribute to total runtime.

Speculative turns and parallel read-only scoring are out of scope.
Another agent owns these changes through `plans/ai-multithreading.md`.
This plan adds no task scheduling, speculative forks, dependency tracking, or parallel loops.

### Completion bar

Each area needs a concrete reduction in redundant work or a documented reason for no change.
Behavior-preserving phases must preserve decisions, authoritative hashes, and RNG state.
Behavior-changing phases must preserve determinism and save/load consistency.
Code inspection and permitted focused checks support these claims. Record all unrun checks.
Do not claim numeric speedups without measurements.

### Runtime restriction and priority

Deliver the speed improvements without making benchmark results a prerequisite.
The user reports that the E2E suite now takes about eight minutes; E2E tests may be run when they provide relevant coverage.
Do not run the default benchmark without approval. Its preparation includes 99 AI turns, and no reliable before/after comparison is currently available.
Do not create a replacement simulation benchmark as an implementation prerequisite.

Before running any test, inspect its fixture setup and transitive simulation calls.
Prefer small constructed states for focused tests. Use a 30-second process timeout for focused test commands; stop after a timeout without automatic retries.
If a focused test is unsafe or times out, record the gap and continue with build checks and inspection.
Do not wait for benchmark results before implementing the next improvement.

## Shared Design Constraints

### Ownership and invalidation

Keep mutable caches local to one simulation and planning segment.
Never store simulation state on the shared `StandardAi` instance or in `AiCatalog`.
A planning segment ends before any authoritative mutation.

Initially invalidate all state-dependent caches after every successful command.
Also audit direct planner mutations and event callbacks that bypass `AiContext.Issue`.
`Refresh` must discard derived entity lists and indexes.
A command counter alone is not a sufficient mutation detector without this audit.
Prefer narrower cache lifetimes over a new global mutation-version framework.

Immutable geometry can survive commands only when its map dimensions and wrap behavior remain unchanged.
Cached paths and production eligibility cannot rely on geometry alone.
Caches must not alter state hashes or consume RNG.
New strategic goals and missions are authoritative state, not caches.
Register, serialize, hash, clone, and reset these records through existing state-component contracts.

### Determinism and behavior changes

Preserve score arithmetic, tie-breaks, fallback order, and command order in Phases 1–4.
Use explicit ordinal content IDs and stable entity or tile IDs.
Do not replace full ranking with a single maximum when callers need fallback choices.
Do not prune a candidate unless a cheap rule proves rejection or a score bound proves irrelevance.

Phase 5 introduces deliberate strategic inertia and mission persistence.
Record these changes separately from transparent optimizations.
Any bounded shortlist that changes choices belongs in Phase 5, not Phase 3.

### Integration with concurrent work

The multithreading implementation is recorded on branch `fast-ai`; begin implementation from its final integrated commit, not from `main` unless that commit has been merged there. The current recorded branch head is `efb49f1`. Confirm the actual base commit before each phase and do not overwrite its changes.

The completed architecture changes these constraints:

- **Scoring concurrency:** Candidate scoring is parallel for single-player AI work. During a speculative player wave, `Simulation.IsParallelAiTurn` makes scoring serial to avoid nested parallel loops. Do not expect candidate-level parallelism inside those waves.
- **Shared planners and pathfinding:** Changes to planners or pathfinding must remain safe both for standalone scoring and for concurrent AI forks. Keep mutable search data and segment caches local; do not add shared mutable service caches. Initialize any shared immutable lazy data before concurrent reads.
- **Forks and authoritative writes:** Speculative players plan on cloned state. Accepted plans are replayed on the authoritative simulation through top-level `TryApply` commands; direct state or extension mutations are not automatically committed. Persisted goals, mission creation, updates, and cleanup must be represented by replayable commands or a deliberately implemented and reviewed commit contract. Do not assume cloning alone makes direct writes safe.
- **Conflict validation:** The completed implementation checks RNG and ID allocation, plot/unit/city changes, player/team/global digests, and entity aggregates, plus active-footprint proximity and relevant war/building constraints. New intent can add dependencies these checks do not model. Inspect actual conflict behavior on the base commit; defer any intent whose dependencies cannot be validated safely. Do not weaken existing conservative invalidation to increase speculative commits.
- **Tests and documentation:** Coordinate edits to AI test owners and `docs/DESIGN.md`; extend existing coverage instead of duplicating it.

The multithreading plan documents an E2E failure (`Unit cannot attack`) that was independently assessed as wave-independent and pre-existing, five pre-existing city-capture test failures, and no reliable before/after speedup ratio. These are known limitations, not evidence that this plan's work caused them or resolved them. E2E tests may be run under the updated runtime expectations, but do not claim a numeric speedup without comparable measurements.

Phase 5 may proceed only after confirming the implementation base and verifying that each proposed intent update survives speculative command replay and that its decision dependencies are covered by current validation. If not, defer that piece and continue with independent work.
